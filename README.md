# PWA Toolkit

Turn a pilot working agreement PDF into searchable text, then ask it questions in plain
English from Claude Code.

Built for the Delta Pilot Working Agreement — a ~600-page PDF that is nearly impossible to
use on a phone at the gate — but the pipeline is not Delta-specific. Any long, sectioned
agreement with running page headers and a table of contents will go through it.

Two halves, usable independently:

- **An ingestion pipeline** (`pipeline/`) that extracts the PDF to per-section text files.
  It lifts pages verbatim from the PDF's own text layer wherever that text is sound, and
  spends Claude vision calls only on the pages that genuinely need it — about 16% of the
  contract. A full run takes minutes.
- **Claude Code skills** (`.claude/skills/`) that search the extracted text and answer
  questions with citations, personalized to a pilot's hire date, aircraft, base and status.

## Quick start

```bash
git clone https://github.com/bronco21016/pwa-toolkit
cd pwa-toolkit

python3 -m venv .venv && source .venv/bin/activate
pip install -e .

cp .env.example .env          # add your ANTHROPIC_API_KEY
cp pilot_profile.example.md pilot_profile.md   # fill in hire date, aircraft, base

mkdir -p data/original
cp /path/to/your-pwa.pdf data/original/live-contract.pdf

python3 pipeline/extract_contract.py --dry-run   # free: reports what needs OCR
python3 pipeline/extract_contract.py             # extract (this is the part that costs)
python3 pipeline/split_contract.py               # cut into sections/, loa/, mou/
```

Then, in Claude Code from the repo root:

```
> what's my rest requirement after a redeye?
> how much vacation do I accrue at 8 years?
> /contract can I be drafted on my day off?
```

The `contract` skill triggers on its own for pilot-job questions; `/contract` invokes it
explicitly.

### Requirements

- Python 3.10+
- **poppler** (`pdftotext`, `pdftoppm`) — `apt install poppler-utils`,
  `brew install poppler`, `pacman -S poppler`
- An [Anthropic API key](https://console.anthropic.com/settings/keys) — for ingestion only.
  Searching an already-extracted contract costs nothing.
- [Claude Code](https://claude.com/claude-code), for the skills

## What you get

```
data/sections/section_NN_*.txt   # one file per contract section
data/loa/loa_NN_*.txt            # one file per Letter of Agreement
data/mou/mou_NN_*.txt            # one file per Memorandum of Understanding
data/handbooks/*.md              # optional reference handbooks
data/INDEX.md                    # generated index: titles, page ranges, filenames
```

Plain text, greppable, one file per document, with the original layout and left-margin line
numbers preserved on every page that came from the text layer.

`INDEX.md` is what the skill reads to find its way around, and it is **generated by the
split**, not kept in this repository — so it always describes the edition actually
ingested, and a listing of the contract's contents never ends up in version control.

## How the extraction works

Most of the PDF already contains exact text. The pipeline's job is to figure out which
pages those are and not touch them.

| Pages | Source | Why |
|------:|---|---|
| 520 | `pdftotext -layout`, verbatim | Sound text layer |
| 97 | Claude vision (`claude-sonnet-5`) | 54 image-only, 43 in a broken font encoding |

Figures are for the February 2026 Delta edition, 617 pages.

Three things make it work:

- **A free dry run.** `--dry-run` classifies every page and reports exactly how many need
  vision and why, without an API call. You know the cost before you spend it.
- **A decoder, not just an OCR fallback.** Some pages are set in a font with a custom
  encoding — `LOA` extracts as `/2$`. It turns out to be a uniform −29 character shift, so
  it is *recoverable* rather than lost, which beats OCR because you get the original text
  back rather than a transcription of it. Decoding is conservative and token-by-token,
  since ordinary text (`UNDERSTANDING`, `2026`, the rest-facility code `4A/2D`) unshifts
  into plausible-looking nonsense; a token is only decoded when unshifting it reveals a
  word the document actually uses. Pages where just the header is encoded therefore keep
  their exact text layer instead of going to the model.
- **A splitter that re-derives itself.** Documents are identified from the running page
  header and titled from the table of contents — both read out of the document — so a new
  edition splits correctly with no hand-maintained anchors.

Per-page caching means a rerun after a failure only redoes what failed.

Full detail, including verification: **[docs/pipeline.md](docs/pipeline.md)**.

## The skills

| Skill | What it does |
|---|---|
| `contract` | Searches the extracted text and answers pilot questions with citations. Reads `pilot_profile.md` to pre-compute longevity year, retirement date and category freeze, and to know the pilot's aircraft, base and status. Knows that the PWA binds and the handbooks only explain. |
| `update-contract` | Runbook for ingesting a new edition — back up, clear cache, extract, split, verify against Section 29 C. and the pay tables. |

Both live in `.claude/skills/` and are picked up automatically by Claude Code when you work
from the repo root. `/contract <question>` invokes the search skill directly.

A few things the search skill gets right that a generic grep does not:

- **Pay questions return every model in the type.** A pilot on the 320 can be assigned an
  A-319, A-320, A-321 or A-321N on any given trip and is paid at the rate of the model
  actually flown — so a single rate is the wrong answer.
- **It never assumes line holder vs. reserve.** That changes every bid period, isn't in the
  profile, and flips the answer on a lot of provisions. It asks.
- **It ranks authority.** The PWA binds; the MEC handbooks explain and may lag. When they
  conflict, the skill says the contract controls.

## Reference handbooks (optional)

The MEC PBS and Scheduling reference handbooks are screenshot-heavy, with much of their
substance as text inside images — no text layer worth lifting. They go through a separate
path using the Message Batches API (asynchronous, half price):

```bash
mkdir -p data/original/handbooks
cp /path/to/handbook.pdf data/original/handbooks/

python3 pipeline/transcribe_handbooks.py submit
python3 pipeline/transcribe_handbooks.py poll
python3 pipeline/transcribe_handbooks.py collect
```

## Configuration

| Variable | Default | Purpose |
|---|---|---|
| `ANTHROPIC_API_KEY` | — | Required for ingestion |
| `PWA_DATA_DIR` | `./data` | Where PDFs and extracted text live |
| `PWA_MODEL` | `claude-sonnet-5` | Model used for page transcription |

Read from `.env` at the repo root, or from the environment.

## A note on the documents

**This repository contains no contract text, and no listing of what the contract
contains.** It is tooling; you bring your own PDF. `data/` is gitignored in full — the
extracted text, the source PDFs, and the generated `INDEX.md` alike — and so is
`pilot_profile.md`. The skills carry instructions and pilot vocabulary only; every section
number, title and rate they use is read out of your ingested copy at query time.

That is deliberate. A collective bargaining agreement is a copyrighted work belonging to
the parties that negotiated it, and a pilot's hire date, seniority number and date of birth
are not things to push to a public remote. If you fork this, keep it that way — check
`git status` before your first commit and make sure `data/` and `.env` are not in it.
